## Bro icon failure and correction

The actual-GL --editor-hammerbro capture reproduced a blank default top card
while placed art and variant-window icons were visible. A fresh focused probe
then showed **four manifest frames but zero cached frames** for
spr_hammerbro_res. The icon Resource was accessed before SpriteLibrary was
ready; its empty lookup survived initialization. A constant Resource property
access could also retain that early null return. Previously, the controls test
selected variants before inspecting the icon, which missed the initial path.

- SpriteLibrary resets pre-ready derived caches when loading the manifest and
  never caches an absent metadata entry as an empty animation.
- HammerBroVariant waits for the autoload's ready state and exposes get_icon().
  HammerBroPart invokes that method at runtime for its default icon. The60px
  canvas/48px cropped body is retained; source frame pixels are unchanged.
- Preparation explicitly includes the four default Hammer Bro sprites; these
  defaults are inherited from the script and absent from its base .tres fields.
- palette_icon_test simulates an early library lookup, then uses cold default
  selection. Its GL mode compares the actual colored pixels in the clipped top
  card, center icon and sector icon, allowing the sector's one-screen-pixel
  nearest-sampling boundary at fractional placement. It does not repair the
  texture in the test or disable clipping. The dedicated GL probe passes.
